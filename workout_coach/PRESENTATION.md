## 1. 비전 (Vision)

### 슬라이드 제목
> **"운동 루틴, 이제는 나에게 맞춰진다"**

### 비전 대사 (암기용 스크립트)

> "헬스장에 가서 뭘 해야 할지 몰라서 스마트폰만 보다 나온 적 있으신가요?
> 저는 AI 운동 코치를 만들었습니다.
> 목표와 조건을 입력하면 **나만의 주간 루틴**을 자동으로 추천해주고,
> 매일 운동하면서 세트 수와 횟수를 그 자리에서 바꿀 수 있는 앱입니다.
> '모든 사람이 자신에게 맞는 운동을 할 수 있는 세상'이 이 앱의 비전입니다."

### 비전 한 줄 요약
**"개인화된 운동 경험으로, 누구나 꾸준히 운동하는 세상을 만든다"**

## 2. 문제 정의 (Problem)

### 공감대를 유발하는 3가지 문제

| # | 문제 | 데이터/근거 |
|---|------|------------|
| 1 | **루틴을 모른다** | 헬스장 신규 회원의 60% 이상이 3개월 내 포기. 주된 이유 — "뭘 해야 할지 모름" |
| 2 | **획일적인 루틴** | 유튜브나 커뮤니티 루틴은 모든 사람에게 동일 — 내 목표·장비·요일이 반영 안 됨 |
| 3 | **기록이 귀찮다** | 기존 앱은 기록 입력 UI가 복잡해서 실제로 기록하는 사람이 드뭄 |

### 문제 정의 대사

> "운동을 시작하려는 사람들이 가장 많이 하는 말이 '뭘 해야 할지 모르겠어요'입니다.
> PT를 받으면 해결되지만, 월 20~30만 원은 부담스럽죠.
> 인터넷에 있는 루틴은 내 조건이 아니고, 기록 앱은 쓰기 복잡합니다.
> 저는 이 세 가지 문제를 하나의 앱으로 해결하려 했습니다."

## 3. 솔루션 (Solution)

### 핵심 기능 3가지

```
1. 스마트 루틴 추천
   - 목표(근육/감량/체력/건강) + 요일 + 장비 유무 입력
   - 7개 부위 × 42종목 DB에서 알고리즘으로 맞춤 배분
   - 저장 전에 미리보기에서 원하는 종목으로 교체 가능

2. 세트별 실시간 편집
   - 오늘 운동 화면에서 각 종목 탭 → 세트 상세 펼침
   - 세트 수 + 세트별 횟수를 그 자리에서 +/- 버튼으로 조절
   - 세트 완료 체크 → 운동 기록 저장

3. 월간 통계 대시보드
   - 달력에서 운동한 날 시각화 (부위별 색상)
   - 운동 횟수 / 평균 완료율 / 신체 부위별 바 차트
```

> "이 앱은 Flutter로 만들었습니다. Flutter는 하나의 코드베이스로 iOS, Android, Web, 데스크탑을 모두 지원합니다. 이번 발표는 Chrome Web 버전으로 시연합니다.
>
> 상태 관리는 Riverpod을 사용했습니다. Riverpod은 Flutter의 InheritedWidget 한계를 극복한 라이브러리로, Provider를 타입 안전하게 선언하고, 비동기 상태를 AsyncNotifierProvider로 깔끔하게 처리할 수 있습니다.

## 7. 구현 시행착오 (ADR — Architecture Decision Records)

### ADR-001: 웹 DB 처리 방식

**상황**: sqflite는 웹을 지원하지 않음  
**선택지**:
- A. IndexedDB 직접 사용
- B. 인메모리 구현체로 대체
- C. Firebase Firestore 도입

**결정**: B (인메모리)  
**이유**: 발표 목적상 웹 데모가 필요했고, Firebase 도입은 과도한 복잡도를 추가함. Dart의 조건부 import(`if (dart.library.io)`)로 플랫폼별 구현체를 깔끔하게 분기  
**결과**: `app_database.dart`가 모바일은 SQLite, 웹은 메모리를 자동 선택

---

### ADR-002: 상태 관리 라이브러리 선택

**상황**: Flutter 앱에서 비동기 데이터와 전역 상태를 관리해야 함  
**선택지**:
- A. setState만 사용
- B. Provider
- C. Riverpod
- D. Bloc

**결정**: C (Riverpod)  
**이유**: Provider는 BuildContext 의존성이 있어 비UI 영역에서 접근 불편. Bloc은 보일러플레이트가 많음. Riverpod은 컴파일 타임 안전성과 AsyncNotifier로 비동기 처리가 깔끔함  
**결과**: `AsyncNotifierProvider`로 루틴/기록의 비동기 로딩, 에러, 데이터 상태를 한 곳에서 관리

---

### ADR-003: 루틴 수정 시 기록 보존 문제

**상황**: 기존 `saveRoutine()`이 루틴 저장 시 모든 기록을 삭제함  
**선택지**:
- A. saveRoutine을 그대로 사용 (기록 삭제 허용)
- B. updateRoutine을 별도로 구현

**결정**: B (updateRoutine 분리)  
**이유**: 종목 교체는 루틴 수정이지 초기화가 아님. 사용자가 쌓은 운동 기록이 종목 교체로 사라지면 UX가 크게 저하됨  
**결과**: `AppDatabase`에 `updateRoutine()` 추가, `swapExercise()`는 이를 사용하도록 분리

---

### ADR-004: 루틴 미리보기 vs 즉시 저장

**상황**: 스마트 루틴 생성 후 바로 저장하면 마음에 안 드는 종목을 수정할 기회가 없음  
**선택지**:
- A. 생성 즉시 저장
- B. 생성 후 미리보기 화면에서 수정 후 저장

**결정**: B  
**이유**: 사용자가 루틴을 보고 마음에 안 드는 종목을 교체하는 것이 자연스러운 흐름  
**결과**: `RoutinePreviewScreen` 도입, `_DayCard`를 콜백 기반으로 리팩터링해 저장 전 로컬 상태에서도 재사용 가능하게 설계

---

### ADR-005: 세트 상태 관리 위치

**상황**: 오늘 운동에서 세트 수/횟수/완료 여부를 관리해야 함  
**선택지**:
- A. DB에 바로 저장 (매번 persist)
- B. 화면 로컬 상태로 관리 후 일괄 저장

**결정**: B  
**이유**: 세트마다 DB 쓰기는 성능 낭비. 운동 중 데이터는 임시 상태이고, "기록 저장" 버튼 클릭 시 확정하는 것이 적합  
**결과**: `_WorkoutScreenState`에 `List<List<_SetData>>` 로컬 상태, 저장 시 평균 횟수로 `ExerciseItem` 재생성

## 13. 시연 데모 시나리오 (30초)

### 순서 (매끄러운 흐름)

```

          → 다크모드 토글 버튼 클릭 (즉시 전환 임팩트)

[5-10초] 목표: "근육 증가" 선택 → 다음
          → 요일: 월·수·금 선택, 장비 있음
          → "스마트 루틴 추천"

[10-18초] 부위 선택 (가슴+등+하체) → 종목 수 4개
           → "루틴 생성하기"
           → 미리보기 화면: 벤치프레스 ↔ 버튼 → 덤벨 플라이로 교체
           → "이 루틴으로 시작하기"

[18-25초] 오늘 운동 탭 → 벤치프레스 카드 탭
           → 세트 상세 펼침 → 세트 수 4→5 증가
           → 1세트 10회 → 12회로 수정
           → 1세트 체크박스 완료

[25-30초] 기록 탭 → 달력 + 통계 카드 + 바 차트 확인
           → "이것이 AI 운동 코치입니다!"
```

### 시연 임팩트 포인트

1. **다크모드 즉시 전환** (첫 5초 — 시각적 임팩트)
2. **종목 교체 시트** (사진 포함, 직관적 UI)
3. **세트 편집** (탭 → 펼침 → +/- 실시간 반응)
4. **달력 색상** (부위별 색상 시각화)

## 14. 지속적 개선 의지 + 활용 방안

### 향후 개선 계획 대사

> "현재는 추천 알고리즘이 랜덤 셔플 방식입니다. 앞으로는 운동 기록 데이터를 누적해서 사용자가 잘 완료하는 부위와 못하는 부위를 파악하고, 그것을 기반으로 루틴을 자동 조정하는 적응형 알고리즘으로 발전시키고 싶습니다.

> 장기적으로는 사용자 간 루틴 공유 기능, 운동 영상 링크 연동, 체중·체지방 트래킹까지 확장할 수 있습니다."

## 15. 예상 Q&A 준비

| 예상 질문 | 준비된 답변 |
|-----------|------------|
| "DB가 웹에서 왜 초기화되나요?" | ADR-001 참고. sqflite 웹 미지원 → 인메모리 사용. IndexedDB 도입이 다음 과제 |
| "왜 Riverpod을 선택했나요?" | ADR-002 참고. Provider보다 타입 안전성 높고, Bloc보다 보일러플레이트 적음 |

| "Flutter 선택 이유는?" | 하나의 코드로 iOS·Android·Web 모두 지원. 발표 데모를 Web으로 쉽게 실행 가능 |
| "테스트는 어떻게 했나요?" | 핵심 모델 단위 테스트 + 4개 통합 시나리오 수동 검증 |
| "빌드와 배포 차이는?" | 빌드 = 코드→실행파일 변환 / 배포 = 사용자가 접근 가능한 서버에 업로드 |
